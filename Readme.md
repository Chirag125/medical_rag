# Medical Multimodal RAG — Retrieval-Augmented Generation Pipeline

A retrieval-augmented generation system for question answering over clinical
and scientific literature, combining dense retrieval, cross-encoder reranking,
and grounded answer generation.

**Status: text pipeline complete and evaluated on a 4-document corpus across
two granularities (page-level and document-level recall@5). Chunking-strategy
ablation completed at the document level; page-level ablation built but not
yet run. Multimodal (image) retrieval and full medical corpus integration
planned next.**

---

## The Problem

Clinical and scientific documents combine narrative text, tables, and figures
in ways that text-only retrieval systems handle poorly. A retrieval system
that can jointly index and search across text and images — and ground its
answers with cited sources — is a more realistic fit for how clinicians and
researchers actually need to query literature.

This project builds that system incrementally: text-only retrieval first,
multimodal retrieval next, evaluated against open medical QA benchmarks.

## Architecture

```
Document (PDF)
      │
      ▼
┌─────────────────┐
│ document_loader │  pdfplumber — extracts text + images per page
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│    chunker      │  Parent-child chunking:
│                 │  - Children (256 tok) → precise retrieval
│                 │  - Parents (512 tok)  → context for generation
│                 │  Context headers prepended (doc name + page)
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│    embedder     │  BGE-large-en-v1.5 (1024-dim)
│                 │  Stores in ChromaDB (separate parent/child collections)
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│   retriever     │  Stage 1: BGE bi-encoder → top-20 candidates
│                 │  Stage 2: cross-encoder (ms-marco-MiniLM) → top-5
│                 │  Fetches parent chunks for retrieved children
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│   generator     │  Phi-3-mini-4k-instruct
│                 │  Grounded generation with source citations
└─────────────────┘
```

---

## Why Two-Stage Retrieval

A single dense retriever (bi-encoder) embeds the query and each document
independently — fast, but imprecise, because it never lets the query and
document "see" each other. A cross-encoder reads the query and document
together, producing far more accurate relevance scores — but it's too slow
to run against an entire corpus.

The fix: bi-encoder retrieves a wide net of candidates (top-20), cross-encoder
reranks only those candidates down to the final top-5. This is the same
pattern used in production search systems at scale.

## Why Parent-Child Chunking

Small chunks retrieve precisely (specific enough to match narrow queries) but
generate poorly (not enough context for the LLM to produce a complete answer).
Large chunks generate well but retrieve imprecisely (too much irrelevant text
dilutes the embedding).

The fix: index small child chunks for retrieval, but once a child is
retrieved, fetch and pass its larger parent chunk to the generator. Precision
where it matters (search), context where it matters (generation).

## Evaluation

Recall@5 is measured with a hand-built question set that has known
ground-truth pages/documents, rather than a self-generated one — questions
generated by the same pipeline being tested tend to echo the source chunk's
phrasing and inflate the score. Two evaluation granularities are used:

**Page-level recall@5** (does retrieval find the right *page* within a document):

| Document | Questions | Reranked | Bi-encoder only |
|---|---|---|---|
| GPT-4 Technical Report + System Card (100 pages) | 22 | 77.3% (17/22) | 81.8% (18/22) |
| Self-RAG (Asai et al., 2023) | 10 | ~60% (6/10) | — |

Reranking did **not** improve recall@5 on the GPT-4 report at this sample
size (77.3% vs. 81.8% bi-encoder-only) — a small regression that's within
noise for n=22, but reported honestly rather than assumed away. This is a
plausible, not-yet-explained limitation of the reranker (`ms-marco-MiniLM-L-6-v2`
is trained on general web-passage ranking, not this document's structure)
rather than a bug: it can occasionally demote a genuinely relevant chunk if
a wrong-page chunk shares more surface vocabulary with the question.

**Document-level recall@5** (does retrieval find the right *document* among several):

A 4-document corpus (the GPT-4 report, CoinRAG, Self-RAG, and the Economic
World Models systems paper — two of which are topically adjacent RAG papers)
scored 100% (24/24) reranked, consistently across all three chunking
strategies tested below. This mainly confirms document-level separation
works, including between two papers on the same general topic — it is not
yet a stress test of chunking quality, since telling documents apart doesn't
require fine-grained chunking to succeed.

**Chunking-strategy ablation:**

| Strategy | Document-level recall@5 | Page-level recall@5 |
|---|---|---|
| Naive (flat chunks, no header) | 100% (24/24) | *not yet run* |
| Parent-child + context header (current default) | 100% (24/24) | see table above |
| Parent-child + HyDE (30-chunk sample) | 100% (24/24) | *not yet run* |

Document-level ablation is complete but uninformative (all three strategies
saturate at 100%, as expected — see above). The page-level ablation across
these three strategies is the comparison that should actually differentiate
them; the tooling for it is built (`scripts/ingest_ablation.py` +
`eval_set.json`) but the runs haven't been completed yet.

## Quickstart

```bash
pip install -r requirements.txt
```

### 1. Ingest a full corpus (recommended entry point)

```bash
python scripts/ingest.py
```

Loads every PDF in `data/raw/`, chunks, embeds, and stores fresh each run
(safe to re-run — wipes and rebuilds rather than appending duplicates).

### 2. Query interactively

```bash
python interactive_query.py
```

Loads the retriever and generator once, then takes questions in a loop.
Also reports which extracted images (if any) were referenced by the
retrieved chunks, for checking image-retrieval plumbing.

### 3. Run an evaluation

```bash
python -m src.evaluation.eval --data src/evaluation/eval_set.json --relevance-key page_num
python -m src.evaluation.eval --data src/evaluation/eval_set_multidoc.json --relevance-key doc_name
```

Add `--no-rerank` to get the bi-encoder-only number, or `--persist-dir` to
point at one of the ablation indexes built by `scripts/ingest_ablation.py`.

## Design Decisions

**BGE over OpenAI embeddings.** BGE-large-en-v1.5 outperforms ada-002 on
the MTEB retrieval benchmark and runs fully locally with no API cost or
data privacy concerns — relevant for a medical document use case.

**Context header prepending.** Every chunk is prepended with its source
document name and page number before embedding. Without this, a chunk
saying "the model achieved 94% accuracy" loses all document context once
split — the header recovers it.

**Deterministic generation (`do_sample=False`).** For factual QA grounded
in retrieved context, deterministic generation is more appropriate than
sampling-based generation, which introduces unnecessary variance for a
task where there is a definite correct answer to verify against.

**Token-based truncation for children, character-based for parents.**
Children are embedded through BGE, which has a hard 512-token limit —
truncation must be token-aware. Parents are passed directly to the LLM
as raw text and don't need token-precise truncation, so character-based
truncation avoids subword decoding artifacts.

**Idempotent ingestion.** Early versions of the ingestion script appended
duplicate chunks on every re-run (fresh random IDs for identical text),
which silently inflated retrieval results with redundant hits. `scripts/ingest.py`
now wipes and rebuilds the ChromaDB collections on every run instead.

## Known Limitations (current state)

- Page-level chunking-strategy ablation (naive vs. context-header vs.
  parent-child vs. HyDE) has only been run at the document level so far,
  where it's uninformative (see Evaluation). The page-level comparison —
  the one that should actually differentiate the strategies — is built but
  not yet executed.
- Image retrieval (CLIP) not yet implemented — text-only currently. Initial
  figure extraction also appears limited: `pdfplumber` reliably pulls
  embedded raster images but struggles with vector-drawn figures (plots,
  architecture diagrams), which make up most of the figures in the current
  corpus. This may need page-rendering + region-cropping instead of
  embedded-image extraction to actually work.
- Occasionally, generated answers show an empty sources list despite
  apparently valid retrieval upstream — under investigation, likely in the
  `cross_encoder_score > 0` filter condition in `generator.py`.
- Generation on CPU is slow (roughly 1–5 minutes per query with Phi-3-mini).
  GPU inference or 4-bit quantization would resolve this for production use.
- Low-confidence reranked results (negative cross-encoder scores) are not
  yet filtered out before being passed to the generator.
- RAGAS faithfulness/answer-relevance scoring not yet implemented — recall@k
  is currently the only automated metric.
